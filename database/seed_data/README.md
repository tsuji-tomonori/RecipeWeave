# 正規化カタログの初期投入

`DATABASE_URL`を設定し、移行後に`uv run python -m database.seed`を実行する。
`--dry-run`はDBへ接続せず、元カタログと投入予定件数を確認する。

元のGoogle Sheetsを保存した`spec/database/catalog-source-sheet.json`の1005食品・68軸・924候補値をすべて保持する。食品は`data/catalog/source_foods.json`と全項目を照合し、差があれば停止する。936件の食品同一性は既存のreviewed-v3辞書を引き継ぐ。

`legacy_food_mapping.json`は以前の画面サンプルに使った35食材の移行対応である。鶏肉・豆腐・チーズなど、部位や商品を特定できない13概念を特定の食品へ勝手に同一視せず、別コードで追加する。元カタログと合わせて1018食品、949同一性となる。売場・保管場所などの表示分類もDBの軸・候補・関連テーブルへ保存する。実行APIはこのJSONやマッピングを読み込まない。

既存8レシピは34材料、25工程、材料の中間生成物・受渡し・20依存辺、道具、数量規則、分類、署名に分解して保存する。`recipe_material_flow.json`は旧原稿に不足していた明示的な材料の受渡しと完了条件を補う登録入力である。材料の購入状態や下処理後の重量・歩留まりを実測したものではない。食味の試作や個別商品の表示確認も未実施なので、全件`draft / needs_review`で保存する。構造検査と調理試作を別の`validation_result`に記録し、検索用公開文書は作らない。認証済みのローカル開発用プレビューでのみ閲覧できる。

初期規則の比例換算は材料量の算術計算用であり、時間を人数に比例させない。工程時間の規則は`manual`として人数変更時の再確認を要する。カップ焼きそばの原稿内の3分は商品固有条件が未確認の例であるため、商品の準備規則へ固定値を登録しない。

21個の生成テンプレートは許可された同一性の集合を保持する。役割を限定した副材ペアがあるテンプレートは`support_identity_sets`も保存し、単純な組合せ計算に置き換えて候補件数を増やさない。12,069,539件の設計点を公開レシピとして投入しない。

単位・標準動作・資源など、実際に必要な初期マスタを登録する。商品仕様・栄養値・アレルゲン不使用・メディア・利用履歴など、根拠や実行結果のない行は作らない。テーブルの実装があることと初期行があることは別である。

IDは固定コードからUUIDv5で採番する。同じ内容の再投入では重複しない。既存の同じIDと内容が異なる場合は上書きせず停止し、初期版の更新を要求する。DBのFK・CHECK・RLS・不変版のトリガーを無効化する処理はない。開発用利用者の認証主体は`local:alice`、`local:bob`、`local:admin`であり、パスワードや秘密鍵はデータに含めない。

人数変更時の工程時間は利用者が秒数を入力・確認する。初期版の便宜的な時間上限2人を物理上限として使わないため、新IDの手動時間規則 `time_manual_user_estimate_v2` を登録する。1〜1000はアプリの人数入力範囲であり、試作済み人数や器具の収容能力を示さない。材料の換算規則にある人数範囲と、実際の器具の台数・既知容量は別に検査する。既存DBは005移行で対象8品の下書き工程だけ参照を切替え、旧規則と公開版は保持する。確認秒数は料理の規則を書き換えず、各調理タスクへ `user_estimate` として固定する。
