## 3. Pages 有効化の根拠と残作業

親エージェントが公式 `actions/configure-pages` の `action.yml` を確認した。有効化を行う `enablement` には `GITHUB_TOKEN` では足りず、Pages 書き込み権限の PAT、または必要な administration / pages 書き込み権限を持つ GitHub App トークンが必要である。現在の管理ツールから実行できない設定変更を、他の権限経路で迂回しない。

根拠: https://github.com/actions/configure-pages/blob/main/action.yml

リポジトリへの実装・検証・Actions 成果物は先行して準備する。公開 URL の応答確認が済むまで「Pages 公開済み」としない。

## 4. OCR の利用者向け要件

以下はサービス設計上の判断であり、特定 OCR エンジンの精度保証ではない。

1. レシート画像を読み込み、商品行の候補を表示する。
2. 商品名から食材名への対応を利用者が確認・修正できる。
3. 個数、重量、容量、消費期限が読めない場合は未確定として扱い、推測値を確定登録しない。
4. 合計額、税額、値引き、日用品を食材として自動登録しない。誤抽出行は確認時に除外できる。
5. 同じレシートの再登録を検知する設計と、読み取り失敗時の再撮影・手入力導線を用意する。
6. Dev の端末内処理と、将来クラウド OCR を追加する場合の送信先・保存有無は明示的に分ける。

## 5. API / IAM / マイグレーションの未確認事項

今回、AWS 公式文書から最新仕様を取得できていないため、以下は実装前・デプロイ前の確認項目である。検証済み仕様として記載しない。

- API Gateway の JWT 検証と Cognito の issuer / audience / token 種別・scope の対応。API 側でも利用者 ID に基づく所有権を毎回検証する。
- Aurora DSQL の現在の接続認証手順、IAM 権限、Python ドライバ対応、接続更新方法、トランザクションの制限。
- DSQL が対応する DDL と制約、索引作成の完了確認、マイグレーション管理方式。一般 PostgreSQL 用スクリプトを未検証のまま DSQL 対応済みとしない。
- Lambda の実行権限とデプロイ権限の分離、環境ごとのデータ分離。
- Bedrock 画像入力の利用可否・対象モデル・日本語レシート精度。今回、採用根拠が取得できていないため導入済み・推奨確定とはしない。
