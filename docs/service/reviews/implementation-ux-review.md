# 利用者導線と実装の照合レビュー

確認日：2026-09-06。対象：`frontend/src/App.svelte`、`frontend/src/lib/{domain,persistence,receipt,ocr,types}.ts`、サンプル料理データ、利用者向けmanual／FAQ。

この記録はコードを読んだ独立レビューです。ローカルURLのブラウザ操作、実ユーザーテスト、実レシートでのOCR精度評価は行っていません。記載の再現手順は実行すべき検証手順であり、実機で実行済みとは扱いません。確認中も担当が実装を更新しているため、発見時の根拠と修正再確認を分けて残します。行番号はその時点のスナップショットです。

## 発見事項

### UXI-01 重大：サンプルレシートを在庫へ登録できない

- 発見時根拠：App.svelte 68行の `sampleRead()` が `imageHash='sample-receipt-v1'` を設定。persistence.ts 55行の `validateAppState()` は `imageHash` に64桁の16進文字列だけを認める。登録はAppの `change()`→`transact()`→`validateAppState()` を通る。
- 再現手順：初回状態→レシートから追加→サンプルで試す→選択済み2件のまま「この内容で登録」。保存データ形式エラーで登録が完了しない。
- 文書との関係：manualのサンプル体験、登録手順が最後まで進めない。初回導線を塞ぐ。
- 修正依頼：サンプルも検証規則に適合する固定SHA-256値を使用し、サンプル登録を永続化層まで通して検証する。
- 修正再確認：担当へ通知後のApp.svelte 72行で64桁hexの固定値に変更されたことを確認。**コード上の原因は解消**。永続化を含む操作試験結果は担当の検証記録で別途確認する。

### UXI-02 重大：重複確認で履歴を見ると訂正した候補が消える

- 発見時根拠：App.svelte 148行の重複ダイアログ「履歴を見る」が `navigate('history')`。同43行の `readRoute()` はレシート画面から別ルートへ移ると `clearReceipt()` を実行し、候補・画像・登録IDを破棄する。
- 再現手順：レシート登録済み→同じ画像を読み取り→候補を訂正→登録→重複の警告→「履歴を見る」→元の確認に戻る。訂正内容を失い、画像選択からやり直しになる。
- 文書との関係：manualは履歴を照合して「別の買い物として登録」へ続けられると説明する。必要な照合が破棄操作になっている。
- 修正依頼：候補を保持したまま確認できる履歴シートと戻る操作へ変更する。履歴を開いたことを登録確定・候補破棄と扱わない。
- 修正再確認：担当へ通知後、`modal='duplicate-history'` へ変更、閉じると `duplicate` へ戻す分岐を確認。**ルート遷移による候補消失の原因は解消**。シートから別購入登録へ進む一連の操作試験は別途必要。

### UXI-03 重大：材料量の保存待ち中に作り始めると古い分量を引き継ぐ

- 発見時根拠：App.svelte 39〜40行の `writeQueue` と `change()` は非同期。49〜51行の `updateDraft()`／`changeAmount()` は保存完了を待たない。53行 `addMeal(d)` と75行 `cookSingle()` は呼出時の `draft` を先にキャプチャして次の書込みへ渡す。domain.ts 222〜225行 `startCooking()` は渡されたitemsを調理スナップショットにする。
- 再現手順：材料量を変更→その保存がWeb Locks等で待っている間に「この料理を作る」又は「献立に追加」を押す。後から料理詳細の量は更新されても、調理／献立には変更前の量を使う経路がある。人数を変えた直後も同様。
- 文書との関係：manual「どちらも調整した分量を引き継ぎます」、FAQ Q06に反する。利用者が入力した量と実際に消費する量の不一致につながる。
- 修正依頼：未完了の量更新を待ってから最新stateの料理下書きを取得するか、次のmutator内で最新下書きを読む。人数の連続操作も古いdraftを重ねて上書きしないよう確認する。
- 状態：担当へ共有済み。修正後の再確認対象。

### UXI-04 重大：保存データ破損の表示が消え、バックアップで復旧できない

- 発見時根拠：App.svelte 85行のonMountは `loadState()` 例外でerrorを設定した直後に `readRoute()` を呼ぶ。同43行の `readRoute()` が `error=''` にする。persistence.ts 118〜124行の `transact()` は先に現在の `loadState()` を要求し、129行の `restoreBackup()` も `transact()` 経由。データ消去もAppの `change()` 経由。
- 再現手順：保存領域に破損したJSON／現在版の不正データがある状態でアプリを開く。初期空画面になり、読込エラーは消える。設定から正常バックアップを読み込み、置換を確定しても現在データの読込みで失敗する。UIの消去操作も同じ前提で失敗する。
- 文書との関係：manualとFAQ Q36/Q37のバックアップ復元手順で回復できない。空表示を新規状態と誤認する可能性がある。
- 修正依頼：起動エラーを維持し、現在データを勝手に消さずに、明示確認を伴う正常バックアップからの復旧／対象消去の経路を設ける。破損rawを守り、別タブ更新を検知する。通常の書出しで初期空stateを元のデータと誤認させない。
- 状態：frontend_implとdomain_implへ共有済み。domain担当から専用復旧API（検査・ロック下CAS・明示置換）を実装中との回答。実装を読んで再確認する。

### UXI-05 中：完了確認画面を再読込みすると材料欄が空になる

- 発見時根拠：App.svelte 20行で `consumption=[]`、77行の `prepareComplete()` が調理スナップショットから材料を組み立てるが、呼出元は `nextStep()` のみ。130〜131行は `#/complete` とcookingさえあれば完了画面を描画する。`readRoute()`／onMountでは材料の再構築をしない。`finishCooking()` は空配列を明示的に渡すためdomain側の既定材料にもならない。
- 再現手順：最後の工程→使用量確認画面→ページ再読み込み。材料が空でも「在庫から使用量を引く」と「完了」を操作できる。
- 文書との関係：実使用量を確認してから完了する説明を満たせない。再訪時の復帰にも必要。
- 修正依頼：完了ルートの復帰時に対象セッションの必要量を再構築する。実使用量を編集した下書きまで保持するならセッションIDに結び付けて保存する。空データのまま成功にしない。
- 状態：担当へ共有済み。修正後の再確認対象。

### UXI-06 中：OCR失敗後の「手入力で追加」で入力画面が閉じる

- 発見時根拠：App.svelte 108行のハンドラは `navigate('fridge');openStock();`。その後のhashchangeで `readRoute()` が `modal=''` を実行する。
- 再現手順：OCR失敗を表示→「手入力で追加」を押す。モーダルを開いた後にルート更新で閉じるため、手入力画面に到達できず冷蔵庫で再操作が必要。
- 文書との関係：manual 67行の失敗時に選べる継続手段が一操作で接続されていない。
- 修正依頼：移動後のアクションとして入力画面を開く、又は手入力の状態をルートとして扱う。ルート更新の初期化で消えない順序にする。
- 状態：担当へ共有済み。修正後の再確認対象。

### UXI-07 中：異なる切り方でも半月切りの説明を表示する

- 発見時根拠：App.svelte 153行のguideモーダルは見出しだけ `currentStep.guide`、本文と図は半月切りで固定。サンプルrecipes.jsonのトマトはくし形切り、豆腐は角切り、キャベツはざく切り。
- 再現手順：トマトと卵の料理→最初の工程→切り方を見る。見出しはくし形切りだが半月切りの図と手順が出る。他の2種も同じ。
- 文書との関係：必要な技法を図・文章で確認するB15、FAQ Q33の目的を満たせない。
- 修正依頼：サンプルで参照する4技法をそれぞれの図と説明へ分岐し、未対応なら別技法を代用せず未提供と説明する。
- 修正再確認：担当へ通知後のApp.svelte 158行で半月切り・くし形切り・角切り・ざく切りを別の本文と図へ分岐したことを確認。**コード上の説明の取り違えは解消**。描画結果の見やすさは未評価。

## 確認できた良い接続

- ホームの食材カード全体による選択と未選択チェック、人数を検索入力に置かない構成はコードにある。
- 冷蔵庫行の検索選択と「編集」は独立したボタンになっている。編集では選択配列を変更しない。
- OCR候補はAppの一時state、在庫の永続化は「この内容で登録」のmutatorに分離されている。修正した候補と選択件数を確認できる。
- 完了時の在庫反映チェックは初期OFF。domainの完了済みセッションは再適用しない。数量不明・不足・単位不一致は表示理由とともに減算を見送る。
- 中断した調理はホームと献立から再開でき、ガイドを閉じる操作はルート・工程位置を変更しない。

これは利用者にとっての使いやすさを実証したという記録ではありません。上記の重大事項を修正してから、マニュアルの具体例による受入検証へ進める必要があります。

### 本レビューの終了判定

発見した7件について、原因に対応するコード変更を確認しました。本レビューの範囲に未解消の重大事項はありません。人数操作の待機中に別画面へ移っても操作時の料理IDを保持する最後の修正も、App.svelteの `adjustServings()` を読んで確認しました。

この判定はコード照合の終了です。実ブラウザでの押しやすさ、端末の撮影・画像選択、実画像OCR、Pages公開URLでの再訪・通信・保存は別の受入記録で確認してください。担当のDOM統合テスト追加については、コードが存在することとその合格結果を混同せず、担当の実行結果へ委ねます。
