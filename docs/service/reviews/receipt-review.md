### RR-01 / P1：使用・編集後の取消が操作として完結しない

根拠：マニュアル「登録後に取り消す」、FAQ Q21 は「現在の在庫と調整内容を確認」で止まる。例えば以前から500g、今回300g追加、その後200g使用した食材で、利用者は何g減るのか分からない。合計量を登録前に巻き戻す操作だと誤解する余地がある。

第1回の推奨は、変更済みの追加分は一括取消から外し、未変更の追加分だけを取り消す方式。これを採用する場合の追記案：

> 取消の確認画面には「今回取り消せる分」と「使用・編集したため確認が必要な分」を分けて表示します。「表示した追加分を取り消す」を押すと、前者だけを削除します。後者と、以前からある在庫は変えません。「在庫を確認」から現在の残りを見て、必要ならその在庫を個別に直してください。取り消せなかった分は履歴に残ります。

別案として「変更済みの追加分も個別確認して取り消せる」仕様を選ぶなら、対象の現在量・取消後量を具体的に見せる操作を確定する。単に「確認して調整する」のまま要件へ渡さない。

再確認例：旧在庫500g＋今回追加300g、追加分は未変更／追加分を100g消費／追加分の数量を250gへ編集／追加分を既に削除／今回追加が数量不明、の各状態で結果を説明できること。

### RR-02 / P1：取消後の履歴と二重取消が定義されていない

根拠：FAQ Q18、Q21、画面 R06。「取り消す」の後で履歴ごと消えるのか、取消済みの行を再び押した場合どうなるかが分からない。既に取り消したレシートの再読取が「登録済み」に見えると利用者が止まる。

追記案：

> 取り消した履歴は「取消済み」として残ります。同じ履歴をもう一度開いても、在庫を再び減らす操作はできません。一部だけ取り消した場合は「一部取消」とし、残っている登録を表示します。再登録の確認では、この状態も確認できます。取消済みの買い物をもう一度登録したい場合は、現在の在庫に同じ購入分が残っていないことを確認してから進みます。

重複照合の案内も具体化する：

> 「登録済みの可能性があります」が出たら、「履歴を見る」を押して、登録日時・購入日（読み取れた場合）・食材一覧・登録状態を比べてください。同じ買い物なら「登録をやめる」、別の買い物と確認できた場合は「別の買い物として登録」を選びます。判断できない場合は登録をやめて在庫を確認できます。

購入日や店舗名が読めない場合は「不明」とする。重複検知は候補であり、すべての重複を防ぐ保証として説明しない。

### RR-03 / P1：食品が誤って自動除外された場合に復帰できない

根拠：FAQ Q16 はチェックを外す説明だけ。画像23には「日用品・金額などを除外しました」の折りたたみがあるが、本文はこれを開く操作を説明していない。

追記案：

> 買った食品が一覧にない場合は「除外した行を確認」を開きます。食品の行があれば「食材として追加」を押し、食材名を選んで確認してください。数量は不明のままでも追加できます。原文に行自体がない場合は「候補を手入力で追加」を使います。

これらの操作を実装しない場合は、登録完了後に「手入力で追加」する手順を明記する。操作名だけ追加して未提供ボタンを案内しない。

### RR-04 / P1：端末保存消失の復元可否を利用者が判断できない

根拠：FAQ Q37 の「データを書き出せる範囲を設定で確認」は、書き出し自体が使えるのか不明。消えた後の質問にも答えていない。

Devを端末内保存とする場合の最低限の確定文案：

> 試用版のデータは、このブラウザに保存します。別の端末・別のブラウザには自動では移りません。ブラウザのデータ削除などで失われ、バックアップがない場合はサービス側から復元できません。

書き出し・読込を実装するなら「設定 → データを書き出す」「設定 → バックアップを読み込む」を案内し、読込が現在データを置換するか追加するかまで明記。未提供ならバックアップ機能がないと明記する。

### RR-05 / P1：画像処理・保存の方針が利用者向け説明として未確定

根拠：FAQ Q24 は「送信前に隠す」「画面で確認」であり、送信の有無すら本文から分からない。画像22には処理場所の説明がない。「レシート全体を撮影」とQ24の「不要部分を隠す」も一緒に読むと迷う。

端末内OCR・元画像を保持しない方式を実装する場合の確定文案（実装確認が条件）：

> 画像はこの端末で読み取ります。レシート画像をサービスのサーバーへ送信しません。読取後に画像ファイルは保存せず、確認して登録した食材と登録履歴をこのブラウザに保存します。商品名が見えるように撮ってください。会員番号や決済情報など、読み取りに不要な部分は隠して構いません。

OCR原文・店舗名・購入日時を履歴へ保存するなら保存項目と消す入口を明記。画像を保存しないだけでOCR全文も保存しないとは断言しない。クラウドOCRを追加する場合は処理先と保存期間を案内する。

### 利用価値と再確認

食品だけを候補化し価格を量にしない仕組みは、一品ずつの登録より手間を減らし得る。ただし誤除外からの復帰と取消が曖昧だと、誤登録を恐れて一括登録を使いにくい。RR-01〜05を主要動線として確定する必要がある。実際のOCR訂正量・登録時間・濡れた手の操作性は資料では評価できない。

再確認の最小セット：

1. 食品誤除外から復帰し、価格を量にせず、2行の同じ食品を両方登録できる。
2. 取消前後の履歴状態を説明でき、同じ履歴から2回減らない。
3. 使用・編集済みの追加分と既存在庫が、指定していないのに消えない。
4. 取消済みレシートの再登録警告を見て続ける／やめるを選べる。
5. 保存先・消失時復元可否・画像とOCR原文の保存範囲を説明できる。
6. 指示されたボタンがあり、選択件数・有効状態・登録結果が一つの例としてつながる。

### 資料だけで説明できた復帰例

1. **食品が除外された：**「除外した行」を開き、食材を指定して候補へ戻す。原文に存在しなければ今回の登録後に手入力する。価格は数量にしない。同じ商品名の複数行も勝手に削除されない。
2. **二重登録した：** 冷蔵庫のレシート履歴で登録日時・食材・状態を比べ、対象の登録から「今回の登録を取り消す」。現在の取消対象を確認して「この内容で取り消す」。履歴は取消済みで残る。
3. **登録後に使用した：** 今回の追加分300gから100g使った場合は残り200gのみが対象。以前の在庫は消えず、100g使った履歴も戻らない。数量を編集した場合は変更内容と現在量を確認する。
4. **端末を替える：** 元端末で書き出し、移動先のデータも必要なら先に書き出す。移動先でファイルを選び、置換件数と対象を確認して復元する。これは自動同期やデータ合算ではない。
5. **画像の個人情報が気になる：** 商品名等を残して不要部分を隠せる。画像は端末内処理、登録後の履歴から原画像は開けない。端末の写真アプリにある元写真を消す操作とは別である。

### 実装受入へ引き継ぐ範囲

- レシート確定の連打・再試行と取消済み再実行で、在庫を二重変更しないこと。特にFAQ Q19の予定表現は検証結果に合わせて公開前に更新する。
- 登録元を追える在庫と消費が実装され、旧在庫を消さず、残量・編集後量・数量不明・削除済みの各ケースで確認画面どおりに処理すること。
- 元画像やOCR全文が永続保存・ログ・サーバー送信へ混入しないこと。保存する重複識別情報や履歴が、説明した範囲と一致すること。
- 読込ファイルの検証を置換より前に行い、キャンセル・不正ファイル・保存失敗時に現在データを壊さないこと。
- 形式/容量エラー、OCR誤読と誤除外、未選択行がある登録、復帰操作を実ブラウザで確認すること。

実端末での押しやすさ、実レシートの認識品質、訂正回数と所要時間、継続して使う価値の確認は、その後の利用者確認に残る。この残件を、資料の不整合が未解決であることと混同しない。
