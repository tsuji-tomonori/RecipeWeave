# RecipeWeave サービス概要

文書状態：正規化DB・認証APIへ移行した開発版。画面・業務API・PostgreSQLを接続して動作させる構成です。GitHub Pagesは画面とマニュアル・品質証跡の公開先であり、APIやデータベースの稼働を代行しません。提供中の環境は画面の接続状態と品質レポートで確認してください。

## 何ができるサービスか

RecipeWeaveは、食材を選ぶ、料理を決める、冷蔵庫を管理する、献立と買い物をまとめる、順番に作る流れをつなぎます。料理名が思い浮かばなくても、食材カードを押して候補を探せます。カード全体を押せて、選ぶ前から空のチェックが見えます。人数と材料量は料理を開いた後に調整するため、検索前の入力は不要です。

トップには「偶然の一品」を置きます。選択中の食材と設定した除外条件を守り、保存されている対象料理から選びます。条件に合う公開料理がないときは0件を表示し、架空の候補で埋めません。

## 保存とログイン

公開料理の検索はログイン前にも使えます。冷蔵庫、レシート履歴、保存した料理、献立、買い物チェック、調理状況、設定はログインした利用者のデータとしてサーバーへ保存します。同じ利用者で別端末からログインすれば、保存済みの続きが開きます。

レシピ、材料、数量の単位、工程、在庫、献立、利用者等はそれぞれ対応するテーブルで管理します。画面を表示する際の通信にはJSONを使いますが、業務データを一つのブラウザ保存や一つの巨大な状態JSONへ押し込む方式ではありません。

同時に更新されていた場合は、古い内容で上書きせず最新の状態を読み込むよう案内します。通信が失敗した操作は完了扱いしません。

## 主な操作

| したいこと | 入口 | 結果 |
|---|---|---|
| 食材から料理を探す | ホーム → 食材カード → 探す | 条件に合う保存済み料理 |
| 手持ちの食材を使う | 冷蔵庫 → 食材を選ぶ | その食材を使う候補と量の確認 |
| レシートをまとめて登録する | 冷蔵庫 → レシートから追加 | 確認した食品だけを在庫へ登録 |
| 登録を取り消す | 冷蔵庫 → レシート履歴 | 未使用・未編集の追加分だけを取消 |
| 分量を調整してまとめる | 料理詳細 → 献立へ追加 | 料理別の人数・材料量と買い物 |
| 作り方の続きへ戻る | 献立／調理を再開 | 保存した工程の続き |
| 結果の根拠を確認する | 品質レポート | 実テスト・画面証跡・自動生成設計 |

「冷蔵庫」は冷蔵品だけでなく、冷凍・常温品、即席食品や惣菜も扱います。数量が分からない場合は不明のまま保存し、0や推測したグラム数へ置き換えません。

## レシートの扱い

画像は端末内で読み取ります。食品候補を確認し、「この内容で登録」を押すまでは在庫を変えません。金額を重量に使わず、期限もレシートから推測しません。元画像と読取全文はサーバーへ送信せず、確認した食品・量・単位と重複確認・取消に必要な識別情報を送ります。

同じ登録の再送で二重に増やさないようにします。取消時は登録後に使用・編集した在庫を保護します。例えば300gを登録して100g使った在庫は、残り200gを勝手に消さず残します。不要なら、その在庫を個別に確認して編集してください。

## 開発用レシピと公開状態

初期投入の8品は未試作の開発確認用データです。認証した開発環境のプレビューで確認し、通常の公開検索へは出しません。実際に公開する料理は、その料理版の材料・工程・検証・公開状態を確認してから提供します。未試作の8品を本番提供済みの料理数として数えません。

開発環境でのテスト成功、GitHub Pagesの公開成功、AWS上のAPI・認証・DBの稼働成功は、それぞれ別に確認します。APIの接続先が未設定・未稼働なら接続エラーを表示し、端末内の見本へ自動的に切り替えません。
